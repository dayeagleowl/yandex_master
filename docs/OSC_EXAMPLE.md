# Пример OSC: что мастер шлёт в зону

Живой транскрипт, снятый со стенда `zone_stub_stand.toe` — это ровно то, что уходит из мастера в зону. Ниже всё для **зоны 2**; для остальных зон меняется только число в адресе (`/zone1/…`, `/zone3/…`, `/zone4/…`).

Мастер `10.10.10.10` → зона 2 `10.10.10.12`, **UDP порт 6000**.
Обратно зона → мастер `10.10.10.10`, **UDP порт 6002**.

---

## 1. Старт сцены

```
/zone2/start  guestCount:int  p1:int  p2:int  p3:int  force:int
```

**Аргументов всегда пять.** Промптов всегда три слота: неиспользованные — `0`. Порядок промптов = порядок гостей: `p1` — промпт гостя 1, `p2` — гостя 2, `p3` — гостя 3.

**Читать нужно ровно `guestCount` первых слотов, остальные игнорировать.** Мастер берёт промпты по гостям именно этой сессии, а незанятые слоты обнуляет — промпт прошлой группы туда попасть не может. Пришло `1 12 0 0 0` — значит гость один и промпт у него `12`, а не «три гостя, у двоих промпт 0».

| Ситуация | Пакет |
|---|---|
| 3 игрока: промпты 3, 6, 9 | `/zone2/start 3 3 6 9 0` |
| 2 игрока: промпты 3, 6 | `/zone2/start 2 3 6 0 0` |
| 1 игрок: промпт 3 | `/zone2/start 1 3 0 0 0` |

Последний аргумент — `force`: `0` — штатный запуск, `1` — принудительный (оператор нажал ПРИНУДИТЕЛЬНО: зона обязана немедленно прервать что делает и начать с нуля, игнорируя свои блокировки).

`/zone2/restart` — те же пять аргументов, смысл «начать эту же сцену заново».

**В ответ зона обязана прислать:**

```
/zone2/session/start          → на 10.10.10.10:6002
```

Это подтверждение доставки. OSC идёт по UDP, пакет может пропасть молча — мастер считает старт доставленным только по этому ответу. Ответа нет 1.5 с — мастер шлёт `start` повторно (всего 3 отправки), потом зажигает «НЕ ОТВЕТИЛ» в пульте. **Повторный `start` до ответа — это тот же самый старт, а не новая группа.**

## 2. Поток трекинга

Начинается сразу после `session/start`, идёт 30 раз в секунду, по пакету на гостя:

```
/zone2/guest/1/pos  0.0    0.50      ← гость 1
/zone2/guest/2/pos  0.37   0.21      ← гость 2
/zone2/guest/3/pos  0.61   0.83      ← гость 3
```

Два float, оба **относительные внутри зоны, 0…1**:

- `zx_rel` — вдоль движения: **0 = гость входит в зону**, 1 = выходит. Пересчёт из метров и разворот шкалы делает мастер, зоне про метры и про направление думать не нужно.
- `zy_rel` — поперёк тоннеля, 0…1.

`idx` в адресе — от 1 до `guestCount` из старта, **тот же порядок, что промпты**: гость с `idx=2` — это тот, у кого `p2`.

Сопутствующее:

```
/zone2/time  12.0            ← 1 Гц, сколько секунд идёт ЭТА сцена (свой таймер зоны)
/zone2/count 2               ← событие: сколько человек физически в зоне; приходит, когда число изменилось
/zone2/guest/2/state 0       ← у гостя 2 ПОТЕРЯН трек (1 — вернулся)
```

`/zone2/count` — это не состав группы. Состав приходит только в `start`.

## 3. Состав изменился без рестарта

Оператор переставил гостей местами или бикон привязался позже:

```
/zone2/update  3  6  3  9
```

Четыре аргумента (без `force`): новый `guestCount` и новые промпты. Сцену **не перезапускать**, только переприсвоить промпты гостям.

## 4. Сброс

```
/zone2/reset  1  0
```

Два аргумента: `1` и флаг `force`.

## 5. Общее для всех зон

```
/show/state     "running"      ← standby | running | finished
/show/heartbeat 647  16756.0   ← 1 Гц, пульс мастера: seq и аптайм. По нему проверять линк; общих часов шоу нет
/show/hello     1              ← мастер поднялся: сбросить сцену и ответить ping
/show/reset     1
/show/finish    1
/show/ping      1
```

`heartbeat`: `seq` растёт на 1 каждую секунду. Пропал дольше 3–5 с — мастер недоступен. Пошёл заново с малого числа — мастер перезапустился.

## 6. Что зона шлёт мастеру (10.10.10.10:6002)

```
/zone2/ping             1                     ← раз в секунду, обязательно (таймаут 6 с)
/zone2/session/start    1                     ← сцена реально пошла (подтверждение старта)
/zone2/session/end      1                     ← сцена закончена → мастер молчит и запускает зону 3
```

Больше ничего. **Звук мастеру не шлём** — триггеры идут напрямую звуковому компу.

Только зона 3 дополнительно шлёт в конце:

```
/zone3/anchor  guestCount:int  t1:str  t2:str  t3:str
```

## 7. Особое для зоны 4

Зона 4 получает всё то же, что и остальные, плюс **итог зоны 3** — токены гостей, пришедшие по цепочке:

```
/zone4/anchor  3  A7F3  B2K9  C5M1
```

Токенов всегда три, лишние — пустые строки: `/zone4/anchor 1 A7F3 "" ""`. Читать нужно первые `guestCount` штук.

Код группы с панели — вместе со стартом (и ещё раз после `session/start` зоны 4):

```
/zone4/start   2 12 3 0 0
/zone4/code    "233C"          ← на брелоке: session 233C, суффикс -G1/-G2 добавляет зона
```

За ~20 с до конца сеанса панели — пересланный как есть prealert, одна строка JSON:

```
/zone4/prealert  {"event":"prealert","session":12,"code":"233C","uuid":"…","seconds_left":19.8,
                  "guest_count":2,"prompt_ids":[12,3,0],
                  "guests":[{"guest":1,"code":"233C-G1","prompt_id":12,"prompt":"…"},…]}
```

Ещё два сообщения только для зоны 4:

```
/zone4/zone3started  1      ← зона 3 подтвердила старт: группа скоро придёт
/zone4/leave         1      ← следующая группа собрала промпты на панели: показать «пора уходить»
```

Anchor зоне 4 приходит трижды (как только зона 3 его прислала, вместе со `start` зоны 4 и после её `session/start`) — это один и тот же итог, принимать как обновление.

В эмуляторе для этого есть кнопка **ANCHOR ОТ ЗОНЫ 3** (подпись меняется, когда выбрана зона 4), а сами токены задаются полями `Token1..3` — можно прогнать свои строки, а не демонстрационные.

## Полный транскрипт со стенда

Прогон из живого мастера, лог приёмника зоны 2:

```
/zone2/start          3 3 6 9 0    3 гостей, промпты [3, 6, 9]
-> /zone2/session/start            ОТВЕТ: сцена пошла, мастер начнёт слать позиции
/zone2/guest/1/pos    0.000 0.500
/zone2/guest/2/pos    0.370 0.210
/zone2/guest/3/pos    0.610 0.830
/zone2/time           12.0
/zone2/guest/2/state  0            гость 2: ТРЕК ПОТЕРЯН
/zone2/update         3 6 3 9      промпты переставлены, без рестарта
/zone2/reset          1 0          сброс зоны
/zone2/start          2 3 6 0 0    2 гостей, промпты [3, 6, 0]
-> /zone2/session/start
/zone2/reset          1 0
/zone2/start          1 3 0 0 0    1 гость, промпт [3, 0, 0]
-> /zone2/session/start
/zone2/restart        1 3 0 0 0
-> /zone2/session/start
/zone2/start          3 3 6 9 1    3 гостей, промпты [3, 6, 9], ПРИНУДИТЕЛЬНО
-> /zone2/session/start
```

Готовый приёмник, который это разбирает и отвечает, лежит в репозитории: **`zone_stub_stand.toe`** — открыть, поставить `Zone = 2`, вписать IP мастера, и он покажет всё приходящее таблицей. Полный контракт — [`PROTOCOL.md`](PROTOCOL.md) и [`../protocol.json`](../protocol.json).
