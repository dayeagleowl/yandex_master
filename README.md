# master_project_v1 — мастер-проект инсталляции DEEPTECHNIGHT

TouchDesigner **2025.33070**

## Что это

Мастер-проект: принимает трекинг BlackTrax, пересчитывает позиции гостей в единицы зон и (дальше) раздаёт тайминг, команды и данные на компы зон (слейвы).

## Две группы в тоннеле: сессии, гости, промпты

Пока группа одна, «гость 2» однозначен. Как только первая группа дошла до зоны 3 и заходит вторая — нет: гости нумеруются 1/2/3 **внутри своей группы**, а трекинг знает только физический ID бикона. Развязка:

- **Номер сессии** (`Sessionnum`, инкремент) — для людей, логов и адресации зонам; **uuid** — для сверки с панелью. Обе живут в `active_sessions`.
- **`assignments`: бикон → (сессия, гость 1..3)** — привязка живёт от входа до выхода гостя из тоннеля, потом бикон свободен для следующей группы.
- **Лимит** одновременных групп — `Maxactive` (по умолчанию 2). Гейт не пустит новую сверх лимита, даже если зоны 1–2 пусты.

Режим привязки — `Assignmode` (переключается кнопкой **ПРИВЯЗКА** в пульте):

| Режим | Как назначается гость |
|---|---|
| `auto` | Первый вошедший в зону входа → гость 1, второй → гость 2. Порядок перепутали — кнопки **СВАП** в пульте. |
| `pool` | Биконы закреплены за слотами (`beacon_pools`: A = 1,2,3; B = 4,5,6), слоты чередуются между группами. Гость = позиция бикона в своём пуле. |
| `manual` | Только оператором: `AssignBeacon(beacon, num, guest)` или кнопки пульта. |

Сессия закрывается сама, когда все её биконы вне зон дольше `Exitgrace` (8 с): биконы освобождаются для следующей группы. Зонам об этом ничего не сообщается — они о сессиях не знают. Сводка активных групп с гостями, биконами, зонами и промптами — колонка **ГРУППЫ В ТОННЕЛЕ** в пульте.

## Потоки: что уходит и что приходит

Полный контракт с типами аргументов — [`docs/PROTOCOL.md`](docs/PROTOCOL.md) и машиночитаемый [`protocol.json`](protocol.json), готовые примеры пакетов — [`docs/OSC_EXAMPLE.md`](docs/OSC_EXAMPLE.md). Ниже — короткая выжимка.

### Мастер → зоне N (её порт 6000)

| Сообщение | Аргументы |
|---|---|
| `/zoneN/start` | `guestCount p1 p2 p3 force` — запуск сцены одной пачкой |
| `/zoneN/restart` | те же аргументы |
| `/zoneN/update` | `guestCount p1 p2 p3` — состав изменился, **без** рестарта |
| `/zoneN/reset` | `1 force` |
| `/zoneN/guest/<idx>/pos` | `zx_rel zy_rel` — поток 30 Гц |
| `/zoneN/guest/<idx>/state` | `tracked` — 0 трек потерян, 1 вернулся |
| `/zoneN/time` | `elapsed` — 1 Гц, таймер сцены этой зоны |
| `/zoneN/count` | `n` — сколько человек в зоне; событие при изменении, не поток |
| `/zoneN/anchor` | `guestCount t1 t2 t3` — итог зоны 3, приходит зоне 4 |
| `/zone4/code` | `code` — только зоне 4: код группы с панели (`233C`) для брелока, со стартом и после подтверждения |
| `/zone4/prealert` | `json` — только зоне 4: пересланный prealert панели за ~20 с до конца сеанса |
| `/zone4/leave` | `1` — только зоне 4: следующая группа готова на панели, показать «пора уходить» |
| `/zone4/zone3started` | `1` — только зоне 4: зона 3 стартовала |
| `/show/heartbeat` `/show/state` `/show/hello` `/show/ping` `/show/reset` `/show/finish` | общее для всех зон; общих часов (`/show/clock`) нет — линк проверяется пульсом `heartbeat` 1 Гц |

**Режим площадки (05.09): одна группа за проход, трекинг — только зоне 3.** `Maxactive=1`, `Poszones=3`: позиции гостей уходят только зоне 3 и только между её `start` и её `session/end`; зонам 1, 2, 4 трекинг не нужен. Ход: панель прислала `session/start` (все промпты выбраны) → старт зоны 1 → зона 1 прислала `session/end` → старт зоны 2 → … → зона 4. Всё по ответам зон; таймеры `Scenelen1..4` — запасной вариант (0 = ждать зону). Любую зону можно запустить руками в любой момент (СТАРТ ЗОНЫ / ПЕРЕЗАПУСК / СБРОС). **Ручной старт без группы от панели** не шлёт пустышку: мастер заводит служебную сессию с составом по умолчанию (`Defaultguests` = 3, `Defaultprompts` = `1 2 3`), и она едет по цепочке как обычная; настоящая группа с панели её перебивает, а не ждёт, гейт и панель её не видят, в конце зоны 4 она закрывается сама. Проверено на ферме: ручной старт → зоны 1–4 с `3 1 2 3`, посреди пришла группа с панели → пошла своим составом, обе дошли до конца, коды группы ушли зоне 4.

**Номер сессии зонам не отправляется.** Зона о сессиях не знает вообще: всё нужное приходит в `start` — сколько гостей и какие у них промпты. Гость внутри зоны — просто `idx` от 1 до `guestCount`, в том же порядке, что промпты. Номер сессии живёт только внутри мастера и в его журналах.

### Мастер ← от зоны N (порт мастера 6002)

| Сообщение | Что делает мастер |
|---|---|
| `/zoneN/ping 1` | раз в секунду; нет дольше 6 с — зона считается упавшей, лампа гаснет |
| `/zoneN/session/start` | **подтверждение доставки старта**: пока не пришло, мастер повторяет `start` (3 раза), потом «НЕ ОТВЕТИЛ». С этого момента начинает слать позиции |
| `/zoneN/session/end` | останавливает поток позиций и запускает зону N+1 тем же составом |
| `/zone3/anchor guestCount t1 t2 t3` | записывает токены гостей и передаёт их зоне 4 |

Больше зоны мастеру ничего не шлют. Звук идёт напрямую звуковому компу, мимо мастера.

### Мастер ← от тач-панели (порт мастера 6001)

Тело сообщения — **одна строка JSON** (штатный режим панели). У всех сообщений общая шапка `event`, `session`, `uuid`, `time`, дальше поля события.

| Сообщение | Что добавляется | Что делает мастер |
|---|---|---|
| `/panel/ping 1` | — | лампа «панель на связи» |
| `/panel/session/guests` | `guests` | заводит запись о группе |
| `/panel/guest/<K>/prompt` | `guest`, `code`, `topic_id`, `prompt_id`, `prompt`, `mode` | запоминает выбор участника |
| `/panel/session/start` | `guest_count`, `prompt_ids`, разбор по гостям | заводит группу в реестр, присваивает номер сессии, при `Autostartzone1` стартует зону 1 |
| `/panel/session/prealert` | `seconds_left`, `guest_count`, `prompt_ids`, `guests[]` | пересылает зоне 4 как `/zone4/prealert` |

`code` в шапке (`233C`) — код группы для гравировки; мастер хранит его при сессии и отдаёт зоне 4. `session` в шапке — сквозной счётчик самой панели, он **не равен** номеру сессии в тоннеле; мастер хранит оба и связывает по `uuid`. Повторный `start` с тем же `uuid` новую группу не заводит.

### Мастер → тач-панели (её порт 6003)

Отдельная записка для команды панели — что учесть, что принять, чеклист: [`docs/FOR_PANEL.md`](docs/FOR_PANEL.md).

| Сообщение | Аргументы | Смысл |
|---|---|---|
| `/panel/ack` | `uuid num guests` | сессия принята; нет ack за секунду — панель повторяет `start` |
| `/panel/gate` | `0` / `1` | окончательное разрешение пускать следующую группу |

## Биконы: как ID бикона становится гостем

**ID бикона** — это номер, который BlackTrax присваивает физическому бикону в своём софте (он же на наклейке). Мастер своих номеров не придумывает: он различает биконы по этому ID и никак иначе.

Цепочка привязки в одну строку: **ID бикона → позиция в комплекте → номер гостя → его промпт с панели.**

Комплект **A** — три бикона для одной группы, комплект **B** — для следующей; они чередуются. Позиция бикона в комплекте и есть номер гостя: первый бикон комплекта — всегда гость 1 своей группы, второй — гость 2, третий — гость 3. Это тот же номер, что человек получил на панели при выборе промпта. Поэтому правило для сотрудника на входе одно: **кто на панели был «гость 1» — получает первый бикон текущего комплекта.** Какой комплект выдавать следующей группе, написано в пульте в заголовке колонки ГРУППЫ В ТОННЕЛЕ. Дальше мастер привязывает бикон сам, как только тот появился в зоне 1.

**ID вводятся в одном месте:** страница НАСТРОЙКА, ряд БИКОНЫ, два поля — «комплект A» и «комплект B», номера через запятую в том порядке, в каком выдаются гостям. **В комплекте ровно три ID** — гостей в группе максимум трое, и номер гостя = место в комплекте. Если вписать больше (например `1,2,3,4,5,6,7`), четвёртый и дальше гостями «по месту» не станут: мастер напишет в журнал «ВНИМАНИЕ: в комплекте A 7 биконов…», а такой бикон получит первое свободное место 1–3. Зоны в любом случае никогда не получат гостя с номером больше 3 — поток и привязка это отсекают. Отсюда они сами попадают в приёмник BlackTrax: мастер слушает ровно те биконы, что записаны в комплектах. Если на площадке у биконов ID вида 101, 102, 103 — вписать их, и всё остальное подстроится (проверено: таблица привязок, подписи на плане и поток зонам работают с любыми номерами). Каждая правка пишется в журнал «было → стало», мусорный ввод не принимается. Режим привязки `Assignmode = pool` стоит по умолчанию; `auto` и `manual` остались для отладки.

Таблица **БИКОНЫ → ГОСТИ** на странице НАСТРОЙКА показывает всю цепочку: бикон, комплект, номер гостя, к какой группе привязан, видит ли его трекинг и в какой он зоне. Каждая привязка пишется в журнал.

### Бикон в глубине тоннеля, калибровка зоны

Бикон, впервые появившийся не в зоне входа, гостем группы быть не может — гости идут через зону 1. Если группа с его комплектом ждёт привязки и уже дошла до этой зоны — это её гость, которого трекинг потерял на входе, он привязывается. Иначе на эту зону заводится **техсессия** (до трёх биконов, подселяются гостями 2 и 3), зона стартует с ней и получает их позиции — так калибруют зону 4, пока группа заходит в зону 1. Гейт, лимит групп и панель техсессии не считают. Приёмник слушает ID `1..Listenmax` (32), так что любой бикон виден на плане серой точкой «бN», даже не из комплектов. Бикон для калибровки пространства выбирается в ряду КАЛИБРОВКА («бикон калибровки»).

### Бикон сменил ID или сел посреди тоннеля

BlackTrax может на ходу переназначить номер бикона: гость шёл как ID 2, и вдруг его нет, а рядом появился ID 14. Мастер это чинит сам (`Autoswap`, вкл): привязанный бикон пропал (`Reidwait` 0.3 с) → свободный ID, который появился только что (`Reidfresh` 3 с) в пределах `Reidradius` (1 м) от последнего места гостя → это тот же гость, привязка переезжает. В журнале «ЗАМЕНА БИКОНА (ID сменился: 2 → 14 в 0.09 м от прежнего места)». Зоны ничего не замечают: им уходит только номер гостя 1–3, и «ТРЕК ПОТЕРЯН» им не отправляется, пока идёт эта пауза. Если рядом никто не появился, а гостя нет дольше `Swapwait` — берётся запасной бикон комплекта R, который появился в зоне группы.

**Кто есть кто, когда номера скачут.** Номера BlackTrax — относительные слоты, бикон гостя посреди сессии может стать ID 15. Поэтому личность гостя держится не на номере, а на **непрерывности позиции**: привязка делается один раз на входе (место в комплекте, если номер совпал, иначе — свободное место 1–3 по порядку появления), дальше пропавший номер + новый номер рядом с последним местом гостя (`Reidradius` 1 м, `Reidwait` 0.3 с, `Reidfresh` 3 с) = тот же человек, привязка переезжает. Новый номер никогда не забирает гостя у бикона, который всё ещё виден, и берётся только ближайший к месту пропавшего — так биконы не перескакивают между людьми. Ошибку оператор правит вручную (НАЗНАЧИТЬ БИКОН). Тумблер `Strictpools` (выкл) включает жёсткий режим «только номера из комплектов» — годится лишь если BlackTrax отдаёт стабильные ID.

**Ручной старт: сколько промптов.** Ряд ЗОНА на странице ШОУ, кнопки ПРОМПТОВ 1 / 2 / 3 (`Manualguests`): ручная сессия заводится на выбранное число гостей, промпты — первые N из последней группы панели (если панели не было — `Defaultprompts`), остальные нули: `/zone1/start 2 12 3 0 0`. Повторный клик по выбранной цифре снимает выбор (0 = состав как у последней группы). Если число сменили, а в тоннеле висит прежняя ручная сессия — при следующем старте заводится новая.

**Углы зоны 3 (страница НАСТРОЙКА, ряд УГЛЫ ЗОНЫ 3).** Ручная калибровка карты B по четырём углам: бикон калибровки ставят в угол, жмут его кнопку (2/3 ДАЛЬНЯЯ, 2/3 ПРОЕКЦИЯ, 3/4 ДАЛЬНЯЯ, 3/4 ПРОЕКЦИЯ — на кнопке появляется ✓), после четырёх — ПОСЧИТАТЬ. Карта считается только по tx (вдоль) и tz (поперёк), высота ty не участвует; в журнале — формула и промах по каждому углу в см. Хватит и трёх углов. ОЧИСТИТЬ — снять все четыре. Таблица `corners3` сохраняется в `settings.local.json`.

**Фантомные биконы.** Приёмник BlackTrax держит последний пакет бикона вечно: бикон выключили или увезли — а на плане он стоит как живой, пока не нажмёшь Reset на ноде. Мастер теперь считает бикон потерянным сам, если его сырые координаты не менялись дольше `Stalesec` (2 с; живой бикон дрожит хотя бы на доли миллиметра). Работает только для источника `live`; в `sim` точки стоят неподвижно по определению. Кнопка СБРОС ВСЕГО дополнительно сбрасывает сам приёмник.

**Руками** (ряд НАЗНАЧИТЬ БИКОН на странице ШОУ): в колонке ВИДНЫЕ БИКОНЫ кликнуть строку нужного бикона (▶), затем **ГОСТЬ 1 / 2 / 3** — бикон становится этим гостем текущей группы; прежний бикон гостя освобождается, если новый был чьим-то — отвязывается. **ОСВОБОДИТЬ** — снять выбранный бикон с любого гостя. Проверено: ID 2 → 14 на 9 см в сторону — перепривязка за 0.3 с, зона получила ноль лишних сообщений.

## Настройки площадки живут в файле

Всё, что настраивают под площадку — IP и порты, ID биконов, калибровка BlackTrax, геометрия зон, таймауты, имена NDI — сохраняется в `settings.local.json` рядом с проектом **само, при каждом изменении**, и загружается при открытии проекта. Файл не в репозитории: обновление `.toe` из git настройки площадки не затирает. Пример структуры — `settings.example.json`. Кнопка **НАСТРОЙКИ ИЗ ФАЙЛА** на странице НАСТРОЙКА перечитывает файл вручную.

## Фильтр трекинга

Тумблер **СГЛАЖИВАНИЕ** на странице НАСТРОЙКА убирает дрожание координат. Окно по умолчанию 0.12 с — рывок доезжает примерно за 0.2 с. Сглаживаются только координаты; флаги трекинга идут напрямую, иначе потеря бикона замечалась бы с задержкой.


**Защита от скачков** (там же, `Jumpguard`, вкл). Бикон не может телепортироваться: если позиция за кадр улетела быстрее `Maxspeed` (4 м/с), мастер держит прошлую позицию, пока новая не продержится `Jumphold` (0.5 с) — тогда это реальный переезд, а не сбой трекинга. Каждый скачок пишется в журнал BlackTrax («СКАЧОК: beacon3: 5.8 м за кадр»). Это отдельно от замены бикона: если BlackTrax пересадил ID на другой маячок — работает автозамена из запаса (см. «Бикон сел посреди тоннеля»).

## Журналы

На экране — четыре колонки в пульте (лог мастера, группы, звук, плюс журналы отправок и компов внутри `show_control`). Таблицы обрезаются и чистятся при открытии проекта, поэтому **всё то же самое пишется в файл**: `logs/2026-09-03_14-20-05_master.log`, один файл на запуск мастера. Колонки — время, часы шоу, источник, событие, подробности; разделитель табуляция, открывается и глазами, и в Excel.

Потоки 30 Гц (позиции, часы, счётчики, пульс) в журналы и в файл не идут — иначе от них не осталось бы ничего читаемого. Тумблер `Logtofile` на `show_control` выключает запись; имя текущего файла видно в заголовке колонки ЛОГ МАСТЕРА.

### Контроль трекинга — доказательство, а не слова

Отдельно ведётся непрерывная запись состояния BlackTrax, чтобы после показа можно было **показать**, что данные приходили, а не убеждать на словах.

Раз в секунду мастер снимает «подпись» потока — координаты всех видимых биконов — и различает три состояния:

| Состояние | Что значит |
|---|---|
| `идёт` | координаты меняются: данные не просто приходят, а живые |
| `замер` | биконы видны, но координаты стоят дольше `Btfrozen` (3 с) — сервер завис или отдаёт кэш |
| `нет биконов` | никого не видно: сервер молчит или потерял всех |

Смена состояния пишется в момент, когда произошла. Плюс раз в `Btreport` секунд (10 по умолчанию) идёт отчёт «всё по-прежнему» — в файле остаётся сплошная лента с отметками времени:

```
14:31:07  трекинг  отчёт трекинга  источник live | состояние идёт | видно 3 (1,2,3) | изменений за 10 с: 28
14:31:12  трекинг  ПОТОК ЗАМЕР (биконы видны, координаты не меняются)  источник live, видно 3
14:31:17  трекинг  отчёт трекинга  источник live | состояние замер | видно 3 (1,2,3) | изменений за 10 с: 0
```

Состояние потока видно и на лампе BLACKTRAX в пульте — она краснеет, если поток замер или биконы пропали.

## Тест без железа: виртуальные гости и имитация панели

Ряд **ТЕСТ БЕЗ ЖЕЛЕЗА** в пульте позволяет прогнать всю цепочку, когда нет ни BlackTrax, ни тач-панели, ни зонных компов.

**Виртуальные гости** — третий источник трекинга (`Source = sim` на `bt_input`, кнопка **ИСТОЧНИК**). Люди двигаются как настоящие, а дальше всё идёт штатным трактом: `zones` считает зоны и относительные координаты, `show_control` привязывает биконов к гостям и гоняет цепочку — то есть проверяется логика мастера, а не симулятор.

- **ВПУСТИТЬ ГРУППУ** — группа встаёт у входа (правый край) в один-три человека.
- **ХОДЬБА** — идут справа налево; скорость — `Simspeed`, разброс по ширине — `Simspread`. С тумблером `Simloop` следующая группа заходит сама через `Simgap` секунд.
- **Мышью по картинке тоннеля** — нажал рядом с точкой и потащил: гость идёт за курсором. Так удобно ставить человека ровно на границу зон и смотреть, что происходит.
- **ПОТЕРЯТЬ ТРЕК** — бикон пропадает и возвращается, как в жизни.

**Имитация панели** — кнопки **ПАНЕЛЬ 1/2/3** шлют мастеру на его же порт 6001 ровно тот JSON, что шлёт `YS_prompt_panel`: шапка с `event`/`session`/`uuid`, выборы по каждому гостю и весь документ сессии. Проверяется весь тракт целиком — приём, разбор, реестр групп, автостарт зоны 1 — без запуска проекта панели.

Пульт рассчитан на **1280×720** (потолок некоммерческой лицензии).

## Привязка BlackTrax к тоннелю и как её проверить

BlackTrax отдаёт координаты в своей системе (начало у камер, оси как получилось, единицы свои). Тоннель живёт в метрах: `x` вдоль (0 у выхода, 15 у входа), `y` поперёк (0..3). Мастер делает **ремап**: по каждой оси две опорные точки «сырое → метры», между ними линейно. Разворот оси и масштаб получаются из точек сами — отдельных переключателей нет. Каналы: `tx` вдоль, `tz` поперёк (`ty` — высота, не используется); если камеры поставлены иначе — кнопка **КАНАЛЫ tx↔tz**.

Из этих метров считается всё: номер зоны, относительные `zx_rel/zy_rel` **внутри зоны** (0..1 от края зоны, не всего тоннеля), точки на плане и поток зонам. Что видно на плане — то и уходит.

### Процедура на площадке (страница НАСТРОЙКА)

Сначала убедиться, что **источник LIVE** (шапка `BT: LIVE`); на SIM живая строка калибровки кричит красным — калибровать по симулятору нельзя.

0. **Найти свой бикон.** Колонка **ВИДНЫЕ БИКОНЫ** внизу: все ID, сырые координаты, метры, «ДВИГАЕТСЯ / стоит». Пошевели своим — всплывёт наверх; клик по строке — он калибровочный (▶).
1. **Точка A.** Встань с биконом в известную точку — по умолчанию угол между зонами 2 и 3 у дальней от проекции стены `(7.5, 3)` (метры вписаны в поля `A→ X м / A→ Y м`, можно любые другие). Жми **ТОЧКА A: БИКОН ЗДЕСЬ** — сырые попадут в `A: сырое X/Y`.
2. **Точка B.** Вторая известная точка подальше по обеим осям — по умолчанию угол входа `(15, 0)`. Жми **ТОЧКА B: БИКОН ЗДЕСЬ**. Всё — ремап построен, точки на плане должны встать по местам.
3. **ПРОВЕРИТЬ** — бикон в третьей точке (по умолчанию `11.25, 1.5`, поля «контрольная точка»): в журнале промах в сантиметрах. Проверено на модели камер с развёрнутой X и масштабом 1.2: 0 см.
4. Ряд **ПОДВИНУТЬ**: сдвиг всей привязки на «шаг, м» (по умолчанию 0.5, поле рядом) — доводка, глядя на план. Сдвиг двигает все биконы сразу.

Значения можно вписать и руками (поля редактируются кликом, Enter). Всё хранится в `settings.local.json`. **В ЖУРНАЛ** — снять текущие числа одной строкой.

Точки A и B лучше брать в зоне камер (зоны 1–3), у выхода трекинга нет; линия между ними экстраполируется на весь тоннель.

## Геометрия тоннеля

Тоннель **15 × 3 м**, четыре равные зоны. **Движение справа налево**: гости входят при больших `x`, зона 1 — вход справа, зона 4 — выход слева.

| Зона | x (вдоль, м) | y (поперёк, м) |
|---|---|---|
| 1 (вход) | 11.25 – 15.00 | 0 – 3 |
| 2 | 7.50 – 11.25 | 0 – 3 |
| 3 | 3.75 – 7.50 | 0 – 3 |
| 4 (выход) | 0.00 – 3.75 | 0 – 3 |
